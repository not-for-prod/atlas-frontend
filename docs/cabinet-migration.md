# Cabinet

The approved cabinet is a single page at `/cabinet`. Its header has a user avatar menu for Profile, Telegram support and the public website. The main content is ordered as issued-card carousel and issuance button, account balance, account top-up tile, then payment history. Account top-up reuses the original lime ActionTile, including its directional icons and rounded shape; the current deposit dialog remains its action. Carousel balances are rendered inside the card face using the same balance component as card detail, with no text repeated below the artwork. The current carousel contains one explicitly labeled demonstration card; it is not a fallback for a failed card request.

Profile retains its existing account controls, local notification switch and real logout action, and opens as a separate `/cabinet/profile` page with a back-to-cabinet link. Issuance and account top-up also open in modals. Clicking a card navigates to the separate `/cabinet/card` page, with a back-to-cabinet link and the same avatar menu. Existing `/cabinet/support`, `/cabinet/issue` and `/cabinet/deposit` links open the same dialogs over the main page; closing returns to `/cabinet` and preserves a validated tariff. Legacy cards and history URLs render the unified page. Unknown routes return 404.

The reloadable card page starts with the card artwork, with its balance and shared visibility toggle inside the front face. Actions follow the card. Card balance remains separate from account balance. It includes top-up, close and info actions, a card flip control, and a card-operation section. Account, reserved and card balances share one visibility preference across client-side navigation. Either existing balance toggle shows or hides all balances, including carousel amounts. A full reload or successful logout resets visibility to hidden. Card-number/CVV reveal remains a separate local interaction. Flipping shows masked number, expiry and CVV placeholders with an unavailable explanation. Real card listing, details, secrets, issuance, top-up, closure and operation pagination still require backend contracts. No financial success or usable payment credentials are fabricated. Card operations display an unavailable state rather than account transactions or invented history.

Account balance and USDT payment history use authenticated backend APIs with their existing loading, sign-in and error states. History fetches the next cursor as the end approaches, retains a keyboard-accessible “Показать ещё” button, stops automatic pagination on error and lets the user retry. Existing visible-tab refresh and precise amounts remain. Account top-up retains the real crypto-address flow and its idempotency/error behavior.

Set `Support.TelegramURL` in the backend `config/config.yaml` (or `ATLAS_SUPPORT_TELEGRAMURL`) to the official `https://t.me/<username>` support contact and restart the backend. The UI reads `GET /v1/support`; no frontend rebuild is required. Until a valid contact is supplied, Profile and the support dialog show a disabled Telegram control and an explanation. No account is guessed. The avatar is a generic user icon until actual profile data is available.

The cabinet is not an authentication guard. Its demonstration areas remain public; backend authorization protects balance, history and deposit requests. Development preview fixtures remain separate and excluded from production.
